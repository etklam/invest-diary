## Problem Statement

Build a partner-based diary workflow for market review.

The owner writes their own diary. A partner account, which can be an AI account or another human account, also writes a diary for the same market day. The product then shows both sides together so the owner can compare reasoning, catch blind spots, and review where their own market read drifted from a more senior analyst style of thinking.

The first version should not embed AI into the app itself. Instead, the system should expose a restricted write path so an external AI agent can create diaries on behalf of a partner account.

## What Makes This Cool

The cool part is not "AI writes a diary."

The cool part is that the product becomes a training surface:

- Same-day, side-by-side comparison between the user and a partner
- The partner can be AI now, human later, with the same data model
- Historical diaries become review material instead of dead notes
- The system shares reasoning while keeping portfolio exposure private

This makes the app feel less like a journal and more like a replay room for decision quality.

## Constraints

- Partner relationships are many-to-many
- Sharing is account-level per partner link, not per diary
- Turning on sharing exposes both historical and future diaries for that account to that partner
- Shared views must not expose stock holdings or similar portfolio exposure data
- The first compare experience only needs one active partner at a time
- AI is not a privileged in-app role, it is just another partner account
- External AI access must use a scoped API key, not the existing cookie login flow
- The first external write capability only needs `create diary`

## Premises

1. Partner is a first-class relationship in the product, not a temporary AI-specific hack.
2. The compare page is the main user-facing value, not an optional extra hanging off the diary detail page.
3. Diary reasoning and portfolio state must be treated as different privacy domains.
4. API keys for AI agents must be scope-limited and account-bound, or this feature will eventually leak too much authority.
5. The first version should optimize for clean model boundaries over maximum feature count.

## Approaches Considered

### Approach A: AI Fast Path

Summary: Add a fixed AI account, a custom API key endpoint for that account, and a minimal compare page without introducing a real partner model.

Effort: Small
Risk: Medium
Pros:
- Fastest path to a working prototype
- Minimal schema churn
- Good for immediate solo testing

Cons:
- Bakes AI assumptions into the product model
- Human partners would require rework later
- Privacy and sharing behavior become harder to reason about as scope expands

Reuses:
- Existing diary create handler
- Existing auth session helpers
- Existing timeline page structure

### Approach B: Partner-Native Core

Summary: Introduce a real partner relationship model, account-level sharing, scoped API keys for external writers, and a same-day compare surface that works for both AI and human partners.

Effort: Medium
Risk: Low to medium
Pros:
- Matches the real product shape
- Supports AI and human partners with the same primitives
- Keeps privacy boundaries explicit
- Avoids a rewrite when the feature expands

Cons:
- Requires schema work now
- Requires a new auth path for API key writers
- Compare queries are more involved than the current single-user timeline

Reuses:
- Existing diary create validation and persistence flow
- Existing request auth context pattern
- Existing timeline rendering and grouping logic

### Approach C: Unified Actor Platform

Summary: Refactor cookie users, partner users, and API key actors into a single actor/credential system before building the feature.

Effort: Large
Risk: High
Pros:
- Cleanest long-term architecture
- Opens the door to more agent actions later
- Unifies write authority across the app

Cons:
- Too heavy for the first version
- Delays user value
- High chance of overbuilding before the compare workflow proves itself

Reuses:
- JWT and session primitives
- Existing user records
- Existing middleware structure

## Recommended Approach

Choose Approach B.

It is the smallest version that still respects the actual product. The product is not "AI diary autofill." The product is "compare my market reasoning against a partner." That means partner identity, sharing boundaries, and compare views all need to be first-class now, not duct-taped in later.

Approach A ships faster but creates debt in exactly the wrong place: data ownership and relationship modeling. Approach C is architecturally elegant but too expensive for a first pass.

## Open Questions

- Should partner links require a mutual accept/invite flow, or can the owner attach a partner account unilaterally in v1?
- Should a partner account be allowed to have both normal web login and one or more external API keys at the same time?
- Should compare group entries strictly by calendar date in the viewer's timezone, or in each author's own timezone?
- When one side has no diary for a given day, should the compare page show an explicit empty slot or hide that day entirely?
- Should the AI write API accept a richer schema later, such as market summary sections or structured tags, or remain aligned with the current freeform diary schema?

## Success Criteria

- A user can create or link a partner account and enable account-level diary sharing for that link
- A user without any partners continues using the app exactly as a normal single-user diary product
- A partner account can still log in normally and write diaries through the existing web flow
- An external client with a valid scoped API key can create a diary for the bound partner account
- The API key cannot read data, manage users, or mutate unrelated resources
- The compare page can show one owner and one active partner side by side for the same day
- Shared compare views exclude holdings and other portfolio exposure data
- Existing single-user diary flows remain stable

## Distribution Plan

This ships inside the existing web application and deployment pipeline.

External agents use an HTTPS API exposed by the same service. API key creation and revocation should be managed inside the app's authenticated settings surface or admin tooling. The current deployment path for the web app covers this feature; no separate package or binary distribution is required.

## Next Steps

1. Add partner relationship models to the database schema.
   Suggested shape:
   - `PartnerLink`
   - `PartnerLinkShareSettings`
   - `ApiKeyCredential` or similarly named scoped key table

2. Define privacy boundaries before writing code.
   - Shared: diary title, content, tags, date, author identity
   - Not shared: holdings, aggregate portfolio state, private trading metrics unless explicitly reintroduced later

3. Add API key authentication for a create-only diary endpoint.
   Suggested implementation path:
   - Keep existing cookie auth unchanged
   - Add a dedicated API key auth utility for specific endpoints
   - Bind each API key to one account and explicit scopes such as `diary:create`

4. Build partner-aware compare queries.
   - Keep the current timeline endpoint for the owner-only view
   - Add a compare endpoint that pairs owner and active partner entries by day
   - Return placeholders when one side has no entry so the compare page still teaches something

5. Build the compare UI as a dedicated surface.
   - Same-day rows
   - Owner on one side, partner on the other
   - Clear author badges so AI and human partners are visually obvious
   - Strong empty states for "no partner" and "no matching entry"

6. Add audit metadata for trust.
   Suggested fields:
   - `createdVia`: `web` or `api_key`
   - `createdByLabel`: short source label such as `openclaw`

7. Cover the risky seams with tests.
   - API key scope enforcement
   - Partner sharing visibility
   - Compare query privacy filtering
   - Single-user regression coverage
